# Travel Planning & Trip Companion App

Responsive React web app (phone, tablet, desktop) installable as a PWA. Takes users through: Discover → Plan → Build Itinerary → Book → Travel → Capture Memories → Share.

Full product spec: @docs/PRODUCT_SPEC.md (read the relevant sections before building each feature; do not skip ahead of the current phase).

## Stack
- React 18 + TypeScript (strict), Vite
- React Router (lazy-loaded routes), Tailwind CSS with design tokens as CSS variables
- Radix UI / shadcn/ui primitives, Framer Motion (restrained), dnd-kit, TanStack Query, TanStack Virtual
- Zustand for client state, React Hook Form + Zod for forms and validation
- Dexie (IndexedDB) for offline data, vite-plugin-pwa for service worker
- MapLibre GL / Leaflet behind a map provider interface (Google Maps can be added later)
- MSW for mock APIs, Vitest + React Testing Library, Playwright for e2e

## Architecture rules
- Feature-based folders: `src/app`, `src/features/*`, `src/components`, `src/services`, `src/data`, `src/mocks`, `src/lib`, `src/types`, `src/styles`.
- Every external service (AI, maps, bookings, weather, auth, storage, notifications) is an interface in `src/services` with a mock adapter. Screens never import a vendor SDK directly.
- Types and Zod schemas live in `src/types`. AI actions are typed, Zod-validated, and applied through the same repositories as user edits. The model never writes data directly.
- No secret API keys in the client. AI and booking calls go through a backend/serverless proxy (mocked for now).
- Mock bookings must be clearly labelled as demo or "not booked". Never fake a confirmed booking or fake live location.
- Location, camera, and notification permissions are requested only in context, after an explanation.

## UX rules
- Mobile-first, but design phone, tablet, and desktop layouts deliberately. Do not just stretch the phone layout.
- Phone: bottom nav and bottom sheets. Tablet: navigation rail. Desktop: sidebar, itinerary + map side by side, docked AI panel.
- Every screen has a real URL. Every screen has loading (skeleton), empty, error, and offline states.
- Light and dark mode. WCAG 2.2 AA, full keyboard support, respect `prefers-reduced-motion`.
- Calm, premium, travel-focused. Avoid random gradients, excess cards, and AI used as decoration.

## Working style
- Work phase by phase (see spec section 42). Do only the current phase. Stop at the end of each phase for review.
- For each phase: outline the plan, implement, run typecheck + lint + tests, check the app in the browser at 390px, 820px, and 1440px widths, then summarize what changed.
- Keep functions and components small. Prefer reusing design-system components over new one-offs.
- Do not add dependencies beyond the stack above without asking.

## Commands
- `npm run dev` - start dev server (http://localhost:5173; dev-only component gallery at `/_design`)
- `npm run build` - typecheck + production build + PWA service worker (uses `scripts/vite-build.mjs`, which adds the Web Crypto flag on Node < 19)
- `npm run preview` - serve the production build (needed for PWA/service worker checks)
- `npm run typecheck` - TypeScript check
- `npm run lint` - ESLint, zero warnings allowed
- `npm test` - Vitest unit/component tests (`npm run test:watch` to watch)
- `npm run e2e` - Playwright tests at 390 / 820 / 1440 px (first run: `npx playwright install chromium`)

## Phase 1 notes (things that are not obvious from the code)
- `/api/*` is mocked **in-page** by wrapping `fetch` (`src/mocks/install.ts`) with MSW handlers, not by MSW's service worker: the PWA's Workbox worker owns scope `/` and a page can have only one. MSW is lazy-loaded on the first API call.
- Trip state: only `draft | planning | ready | archived` are stored. `upcoming | active | completed` are derived by `computeTripState` from the trip's own timezone and the clock service (demo date simulator in Settings). Always read state via `useTrips()` / `effectiveState`, never `trip.state` for display.
- Bookings are always `mode: 'demo'`, `status: 'saved'` via `bookingRepo.saveDemo`; the schema rejects a confirmed demo booking.
- Repositories enforce roles (`requireTripAccess`) and queue every write in `syncQueue`. AI actions go through `applyAIAction` (Zod-validated, undoable).
- Dev environment is Node 18.15: `package.json` overrides `path-scurry`'s `lru-cache` to 10.x and tests use a custom Vitest environment (`src/test/environment.ts`). Both can be dropped on Node ≥ 20.
- Seed data is versioned (`SEED_VERSION` in `src/data/seed.ts`); bump it when fixtures change so existing IndexedDB data reseeds.

## Phase 3 notes
- `/trips/:id/itinerary/*` is **one** route (`ItineraryView`) that serves the day list, `…/day/:n/add` and `…/items/:id`, so opening a sheet never remounts the list behind it. The URLs are unchanged.
- Itinerary edits go through `useItineraryActions`: optimistic cache update → repository write → rollback + toast on failure → refetch. Pure cache updaters live in `planCache.ts`. Every day mutation in `itineraryRepo` ends with `refreshLegs(dayId)` (distance/travel time between stops); don't write items without it.
- Timing rules live in `features/itinerary/schedule.ts` (warnings, busy-day, re-time). The seeded Bali trip is tested to have **no** warnings, so keep fixtures realistic.
- Maps: screens use `TripMap` + the `MapProvider` interface only. MapLibre forces `position: relative` on its container — keep the container inside an absolutely positioned wrapper (see `TripMap.tsx`); jsdom can't catch a collapsed map, so e2e checks its height.
- Split view (itinerary beside map) = desktop, or tablet in landscape (`useSplitView`). Portrait tablet gets a collapsible map strip; phones get a separate Map tab.
- AI: the assistant only *proposes*. Every action is Zod-validated in `useChat`, shown as a card, applied via `applyAIAction` on click (destructive ones ask again), and undoable. Chat state is persisted per conversation; the desktop docked panel width/open state is in `panelStore`.
- Tests that need a map use `createFakeMap()` (`src/test/fakeMap.ts`) through `renderApp(path, { maps })`.

## Phase 4 notes
- Saving anything to a trip goes through `useSaveBooking` (`data/queries/bookings.ts`): `BookingService.createBooking` → only a `demo` result is stored (via `bookingRepo.saveDemo`), a `live` result throws until a real provider adapter exists. Every booking card/panel shows `DemoBadge` ("Saved to trip — not booked"); never word it as confirmed or purchased.
- Hotel search state (stay dates, guests, filters, sort) lives in the URL query (`features/bookings/filters.ts` parses/serialises, defaulting to the trip's dates and party size). Filter chips come from the unfiltered list. Phone/tablet use a filter sheet, ≥1024px a sidebar. Flights use `?leg=return&from&to&date&travellers`.
- Activities and transport are "saved" from itinerary items (`bookable.ts`), keyed by `refId = item.id`. Flight times are read as wall-clock straight from the ISO string (it carries the airport's offset); other times use the trip timezone (`zonedIso`, `bookingWhen(b, tz)`).
- Checklist: the three booking items are derived from saved bookings (`resolveChecklist`), the rest are plain custom items the user can tick or delete.

## Phase 5 notes
- Live Trip (`/trips/:id/live`, `features/live-trip`) is only for `effectiveState === 'active'`; otherwise it shows a friendly "not live" state. Status logic is pure in `liveStatus.ts`: a stored status always wins, an untouched item is *inferred* `in_progress` inside its window, and a missed item is flagged `overdue` for the traveller to confirm. **Never infer `completed`.**
- Location is opt-in (`useLiveLocation`): nothing is requested until the traveller presses "Use my location" after reading why. `point` is always a real fix. Arrival is only a *suggestion* ("Start it"), never an automatic status change.
- Notifications: `features/notifications/rules.ts` is a pure function (trip + plan + clock → candidates with stable `key`s). `NotificationEngine` (mounted in `AppShell`) delivers them through `NotificationService.deliver`, which drops duplicates by `key` and respects per-type prefs. The browser push prompt is only shown via `PushPermissionCard` (after creating a trip, in the notification centre, in Settings) — never on load.
- Emergency numbers are static data in `src/data/emergency.ts` (bundled, so they work offline); add a country there to support another destination.

## Phase 6 notes
- Capture (`features/memories/AddMemory.tsx`): photos are read for EXIF (`lib/media/exif.ts`: capture time + GPS), then resized/re-encoded by `compressImage` (which also strips EXIF from the stored file). Day and activity are attached by time via `attachToPlan` in the *trip's* timezone; the traveller can override. Location is never fetched until its button is pressed; `stripLocationOnPublic` defaults to on.
- Offline upload queue: media is saved to the local `blobs` table first (`storage.upload`), the memory is `uploadState: 'queued'`, and `processMemoryUploads` (`data/uploadQueue.ts`) calls `storage.publish`. `UploadRunner` (in `AppShell`) runs it on load, on reconnect and every 30 s; failures become `failed` and are retried only by the Retry button. Swapping in Firebase Storage means implementing `publish` and `upload` on the storage adapter.
- Stories: `StoryViewer` is one component, full-screen on phones and a centred 9:16 stage on desktop; it does not auto-advance with reduced motion or over video/audio. `stories/:storyId` plays, `stories/:storyId/edit` and `stories/new` use `StoryCreator`. Slides reorder with buttons (no drag-only interaction).
- jsdom has no `URL.createObjectURL`; `src/test/setup.ts` stubs it. Seed version is 7 (adds a Goa story).

## Phase 7 notes
- Publishing (`publicTripRepo.publish`, UI in `features/public-trips/ShareTrip.tsx`) writes a **sanitised snapshot**: no notes, `bookingId`s, confirmation numbers or memory coordinates. Keep it that way when adding fields to items/memories. `visibility: 'link'` pages are reachable at `/t/:slug` but excluded from `listPage` (the feed); `public` ones are listed. Unpublishing deletes the record, so republishing gets a new slug.
- `/t/:publicSlug` lives under `PublicLayout` (no sign-in, no app state). Save / Like / Use This Itinerary go through `useSignInGate` (`data/queries/publicTrips.ts`), which sends signed-out visitors to `/signin` with a return path. "Use This Itinerary" always copies; the original snapshot is never mutated (tested).
- `useDocumentMeta` sets Open Graph tags client-side only. Real link previews need the server/prerender step from the spec (§2): emit the same tags into the HTML for `/t/*`.
- The feed (`PublicFeed.tsx`) is server-paginated (`FEED_PAGE_SIZE` = 6, cursor), filtered by `q`/`destination` in the URL, and row-virtualised with `useWindowVirtualizer` (columns: 1/2/3/4 at <640/640/1024/1536). A "Load more" button is the keyboard/no-scroll fallback.
- Likes are `likedTrips` (Dexie v3). Seed version is 8 (adds 5 public trips, so there are 8).
- Profile tabs are routes: `/profile/{trips,published,saved,memories}`; `/saved` also exists.

## Phase 8 notes
- Sync: every repository write goes through `put`/`del` (`repositories/shared.ts`) into `syncQueue`. `SyncRunner` (in `AppShell`) calls `syncNow` (`data/syncEngine.ts`) when online: batches of 50 to `/api/sync` (mock acks everything), a `conflict` answer means the newer `updatedAt` wins and the user is told. `SyncIndicator` in the header shows pending changes. Don't write tables outside `put`/`del` or the change never syncs.
- `RouteEffects` (shell + public layout) sets the document title, moves focus to `#main` and announces the page after a *page* change (`routeKey`: itinerary day/sheets don't count). It never steals focus from a field being typed in or an open dialog. Public trip pages set their own title via `useDocumentMeta`.
- `PageTransition` (Framer Motion, lazy-loaded, off for reduced motion) wraps the shell's `<Outlet>`. Keep animation to this; no other page-level motion.
- Security: the CSP and headers live in `scripts/security-headers.mjs`, used by `vite preview` and repeated in `vercel.json` (a test keeps them equal). No inline scripts: the theme bootstrap is `public/theme-init.js`. A new third-party origin (fonts, tiles, images, API) needs adding to the CSP, then check `npm run preview` for violations.
- Contrast: `src/styles/contrast.test.ts` checks the tokens for WCAG AA in both themes. Use `border-border-strong` (3:1) for the edge of inputs/buttons/chips and `border-border` only for quiet dividers.
- PWA: `usePwa` (`lib/pwa.ts`) holds the update-ready flag and the install event; `UpdateBanner` and Settings read it. Updates apply only when the user chooses to reload.
- Tests: Vitest runs with 6 workers and a 15 s timeout (jsdom + IndexedDB per file starves on many-core machines otherwise). If a test finishes while repository steps are still running, call `settle()` (`src/test/settle.ts`) before the next reset. The seed fixtures load lazily (`data/seedData.ts`); import `buildSeed` from there in tests.
- Onboarding (`/onboarding/:step`) is real and skippable; Settings → Account links back to it.

## Stock photos
- Cards show real photos, not the generated SVG scenes. Fixtures call `img(id)` → `photoUrl(id)` (`src/lib/stock`), which maps the seed id to a curated Wikimedia Commons photo in `photos.json` (aliases cover trip/public-trip covers). An id with no photo falls back to `placeholderImage`, so a new fixture never breaks. The SVG generator remains the runtime fallback: `installImageFallback` (`main.tsx`) swaps in the illustration if a stock image errors, using the seed stored in the URL fragment (`#s=`).
- Licences require credit: every photo in `photos.json` is shown on `/credits` (a test checks licence, author and Commons page are present, and that no two places share a photo). Never add a photo without those fields; regenerate with `node scripts/curate-stock-photos.mjs` (resumable; Commons rate-limits, so it backs off) and pin hand-picked files under `PINNED`. Don't trust search ranking blindly: review a contact sheet (`scripts/commons-candidates.mjs` writes one) — search once returned a Mississippi seafood photo for a Bali restaurant.
- New image host ⇒ update `scripts/security-headers.mjs`, then run `node scripts/sync-vercel-csp.mjs` to copy the headers into `vercel.json`. Changing any fixture image means bumping `SEED_VERSION`.

## Environments (M1)
- Two environments, two separate backends, never shared: **development** (local `npm run dev`, Vercel Preview from branch `stage-2-dev`, Firebase project `wayfarer-dev`) and **production** (Vercel Production from `main`, Firebase project `wayfarer-prod`). Work lands on `stage-2-dev` first, is verified on its preview, then merged to `main`.
- Config is read once in `src/config/env.ts` (`env`, validated by Zod; `parseEnv` is the tested part). Never read `import.meta.env` anywhere else. A production build wired to a `-dev` project, or the reverse, throws at startup.
- Committed files `.env.development` and `.env.production` hold **public** values only (`VITE_APP_ENV`, `VITE_BACKEND`, Firebase web config). Secrets (AI/booking keys, Firebase service account) are never `VITE_`-prefixed and live only in Vercel environment variables for the serverless functions, scoped per environment. `.env.development.local` is git-ignored for personal overrides (Vite lets `.env.[mode]` beat `.env.local`, so overrides for dev must use this name).
- Vercel builds always run in Vite's production mode, so Preview deployments must override `VITE_APP_ENV=development` (and the dev Firebase values) in the Vercel dashboard under the **Preview** scope; the **Production** scope uses the prod values. Process env wins over the `.env.*` files.
- `.firebaserc` has aliases `dev` and `prod`: `firebase use dev` / `firebase use prod`. Deploy rules and functions to dev first.
- `npm run build:dev` builds with the development env locally. Settings → Environment shows which environment and backend a build is using.
- Auth (M1): `env.backend === 'firebase'` swaps the mock auth for `services/auth/firebase.ts` (Google sign-in, SDK-held session), loaded lazily through `auth/lazy.ts` so the SDK isn't in the first bundle. That backend seeds only the shared catalogue (`seedReferenceData`), never the demo traveller's trips, and hides demo-only controls. The CSP allows Google's `apis.google.com` script and `*.firebaseapp.com` frame for popup sign-in. Real Google sign-in can only be tried once `wayfarer-dev` exists and its values are set in `.env.development.local` (or the Vercel Preview scope).
- Sync (M1): with `env.backend === 'firebase'`, `SyncRunner` sends the queue straight to Firestore (`data/remote/firestoreSync.ts`, chosen in `data/remote/index.ts`) and pulls remote changes on load, on reconnect and every ~2.5 min. Layout is in `data/remote/paths.ts` (`trips/{id}/{days,items,…}`, `users/{uid}/…`, `publicTrips/{id}`); the trip doc's `members` map (uid → owner/editor/viewer, kept in step with collaborators by sync) is what `firestore.rules` reads. The newer `updatedAt` wins; a remote copy never overwrites a local edit that is still queued; a write the rules refuse is dropped with a warning so it can't block the queue. `del()` stores the record's `tripId` with the queued delete (the remote path needs it). Catalogue tables (destinations, places, hotels, flights) are not synced.
- Rules and sync are tested against the emulators: `npm run test:rules` (rules only) and `npm run test:sync` (real sync + rules, `*.emu.test.ts`). Both need Java; neither runs in `npm test`. On Windows the emulator's Java process can outlive the run, so these scripts call `scripts/free-emulator-ports.mjs` first and last. Deploy rules to dev with `npx firebase deploy --only firestore:rules --project dev` (needs `firebase login`, and the Firestore database created in the console).
- CI (M1): `.github/workflows/ci.yml` runs on pushes to `main` / `stage-2-dev` and on pull requests, in three parallel jobs: typecheck + lint + unit tests + build; the emulator suites (`test:rules`, `test:sync`, Java 21); and Playwright e2e at the three widths. CI uses Node 20, so the Node 18 workarounds in `package.json` overrides are harmless there. Make these jobs required checks on `main` in the GitHub branch protection settings.
- Sharing (M1): owners invite by email from the trip page ("Share with people", `features/sharing`). An invitation is `invites/{tripId}__{email}` (`data/remote/invites.ts`); the person who signs in with that *verified* email sees it on Home and accepts, which adds them to the trip's `members` (rules check the invitation offers exactly that role) and writes their own `collaborators` entry (`collab_{uid}`, with name and email). Owners can withdraw invitations and remove people (the removal is a normal queued `del` that sync turns into a `members` change). Invitations are online-only and need `env.backend === 'firebase'` (`sharingAvailable`). Rules and the whole flow are covered by `firestore-tests/rules.test.ts` and `data/remote/invites.emu.test.ts`; after changing `firestore.rules`, redeploy them to the dev project.
- Sign-out (M1): on the Firebase backend, signing out removes the account's data from the device (`data/accountData.ts`: `wipeLocalAccountData` keeps the shared catalogue). `useSignOut` first tries to send the queue and run uploads; if anything is still unsent it says exactly what would be lost and lets the traveller stay signed in. `claimDevice(uid)` runs at every sign-in and wipes a *different* account's leftovers (closed tab, expired session) so they are never shown to, or synced as, the new account. Demo backend: sign-out keeps data, as before.
## M2 notes
- Media (M2): on the Firebase backend photos and voice notes are stored **in Firestore** (`services/storage/firestoreMedia.ts`, lazy via `storage/lazy.ts`), so no Cloud Storage and no billing plan: the free plan has a hard cap. It stays offline-first: `upload` stores the blob locally and returns at once, `publish` (from the upload queue) writes `trips/{tripId}/media/{id}` (Firestore `Bytes`, type, size), `getUrl` uses the local blob or fetches the document and keeps a copy, `remove` deletes both. Rules: members read, editors/owners write, images and audio only, at most 900,000 bytes (a Firestore document holds 1 MiB). Media documents are deleted with their trip.
- `StorageService.limits` (`services/storage/limits.ts`) tells screens what is possible: on this backend no video, files under 900 KB, voice notes capped at 90 s (the recorder stops itself). Photos are shrunk step by step to fit (`compressToFit`); the demo backend keeps files on the device with no such limits. Roughly 3,000 photos fit in the free 1 GiB.
- **Moving media later** (Cloudflare R2 is the plan, see the cost comparison in the conversation notes): write one adapter implementing `StorageService` (`publish` uploads through a short-lived signed URL from a small Vercel function that checks trip membership by asking Firestore as the signed-in person), point `container.ts` at it with bigger limits, add the R2 host to `img-src`/`connect-src`. Nothing else changes. A one-off script can copy existing `media` documents across.
- Known gap: deleting a memory does not delete its stored media document (the delete has an Undo, so it must survive it). Orphans need a cleanup before launch.
- Emulator tests need Node 18's missing global `crypto`: `src/test/emulatorSetup.ts` supplies it.
- Published trips on Firestore (M2): `publicTrips/{id}` (page), `publicSlugs/{slug}` (short link → page id; this is what makes unlisted `link` pages openable without being listable) and `publicTrips/{id}/media/{memoryId}` (photos shown on the page: on this backend publishing rewrites each photo's `mediaUrl` to `public/{pageId}/{memoryId}` and sync copies the bytes there once the page exists, because trip media is members-only). Reads are `data/remote/publicTrips.ts` (feed with cursor, destination filter and client-side text search; by slug; by id), wired in `data/queries/publicTrips.ts` and kept in the local `publicTrips` table as a never-synced cache. Needs the composite indexes in `firestore.indexes.json` (deploy with `npx firebase deploy --only firestore --project dev`; new indexes take a few minutes to build).
- Likes and saves: a write that creates/deletes `users/{uid}/likedTrips|savedTrips/{lk_|sv_ + uid + _ + pageId}` must move the page's `likeCount`/`saveCount` by exactly one in the **same batch** (rules use `getAfter`/`existsAfter`), so counts can't be inflated or drift; sync sends them as one batch (`sendCounted`). Because of that, save ids are predictable, and every remove must go through `del()` (unlike, unsave, saved places, AI chat delete and unpublish were silently not syncing before; the emulator tests cover them). Republishing keeps the counts stored on the server.
- Published-page hardening (M2): the snapshot is built on the publisher's device (`publicTripRepo.publish`, which leaves out notes, booking links and memory coordinates). A server rebuild was considered and **deliberately not built**: the publisher can already read all of that data, so it would only guard against a buggy or outdated client, at the cost of a function that needs the place catalogue and Firestore reads. Instead: (1) `firestore.rules` `validPublicTrip` only accepts the fields the app defines and sane sizes (so nothing unexpected can be added at the top level or in the snapshot, and the page can't be made huge); (2) readers parse every page with `publicTripSchema` (`data/remote/publicTrips.ts`), which drops unknown fields such as a stray `notes` and skips malformed pages. Revisit if pages ever carry data from several people, or before opening publishing to untrusted clients.
- Deleting a memory removes its stored photo after the Undo window (`UNDO_WINDOW_MS` in `data/queries/memories.ts`); closing the app inside that window leaves one orphan, which is fine at this scale. Trip deletion removes all of a trip's media.
- Link previews (M2): `/t/:slug` is rewritten by `vercel.json` to the Vercel function `api/og.ts`, which fetches the built `index.html`, reads the page from Firestore's public REST endpoint (`api/_lib/firestore.ts`, project from `VITE_FIREBASE_PROJECT_ID` — so **set that variable in the Vercel Preview and Production scopes**, otherwise every shared link falls back to the plain app with a 404) and injects Open Graph / Twitter tags (`api/_lib/preview.ts`, everything user-written is HTML-escaped). A photo cover is served as an image by `api/og-image.ts`; an illustration cover can't be drawn by link previews, so they get `public/og-default.png` (regenerate with `PW_CHANNEL=chrome node scripts/make-og-image.mjs`). Unlisted (`link`) pages get `noindex`. Files under `api/` are deployed as functions, so keep tests out of that folder (they live in `src/server`). Relative imports in `api/` use `.js` extensions on purpose. Local check: `FIRESTORE_REST_URL` points the functions at the emulator (used by `publicTrips.emu.test.ts`).
## M3 notes
- Live services are chosen per environment by two public switches in `src/config/env.ts`: `VITE_WEATHER` and `VITE_ROUTING` (`mock` | `live`, default `mock`; `.env.development` sets both `live`, `.env.production` leaves them off). Set them in the Vercel **Preview** scope too, or previews stay on demo data.
- Weather (`services/weather/openMeteo.ts`): Open-Meteo, no key, called from the browser. A forecast reaches 16 days from today, so a trip further out gets an empty list (screens already show nothing for that) rather than an error; WMO codes map to our conditions, including a new `snow`. Free for non-commercial use only: a commercial launch needs their paid plan or another provider (one-file swap).
- Routing (`services/maps/osrm.ts`): OSRM's public demo server draws the real road line under the map's markers (`TripMap` draws the straight line at once, then replaces it; failures keep the straight line). The demo server is for light use: point `BASE` at a service you run or pay for before launch. Itinerary leg times (`refreshLegs`) are still straight-line estimates.
- `connect-src` allows `api.open-meteo.com` and `router.project-osrm.org` (`scripts/security-headers.mjs`).
- India as the main audience: Firestore is `asia-south1` (Mumbai) in `wayfarer-dev-c2efe`, and **`wayfarer-prod` must be created in `asia-south1` too** (the region can't be changed afterwards). Vercel functions run in Mumbai (`"regions": ["bom1"]` in `vercel.json`). Before a public launch also replace the public OpenStreetMap tile server (its policy forbids heavy use) and review the privacy notice against India's DPDP Act (delete-account-and-data already exists).
- AI assistant (M3): `VITE_AI=live` switches the app from the in-page mock to the Vercel functions in `api/ai/` (`chat` streams NDJSON `token`/`action`/`done`/`error`, `itinerary`, `regenerate-day`), through `services/ai/client.ts`. Default is `mock`; turn `live` on in the Vercel **Preview** scope and in `.env.development.local` once a key exists. Provider = Gemini through its OpenAI-compatible endpoint (`api/_lib/ai/gemini.ts`); `AI_BASE_URL`/`AI_MODEL`/key make Groq or others a settings change. **Server-side settings, never `VITE_`:** `GEMINI_API_KEY` (a Vercel *Sensitive* variable; also read by `npm run dev` from `.env.development.local` via `scripts/local-api.ts`, which serves `api/ai/*` in dev), optional `AI_MODEL` (default `gemini-3.1-flash-lite`; Gemini 2.5 models were retired, so model ids change: check ai.google.dev/gemini-api/docs/models), `AI_DAILY_LIMIT` (credits per person per day, default 20: chat 1, regenerate a day 2, draft an itinerary 3). The functions also need `VITE_FIREBASE_API_KEY` and `VITE_FIREBASE_PROJECT_ID` (already set for previews).
- How it is kept safe: every call needs a Firebase ID token, verified with Firebase (`api/_lib/ai/http.ts`); bodies are size-capped and schema-checked (`schemas.ts`, a deliberate copy of the app's action schemas because Vercel can't import app source; `src/server/ai.test.ts` fails if the copies drift); the model can only call functions (`tools.ts`) and every proposal is dropped unless its ids exist (places from the catalogue the app sends, activities and days from the plan the app sends); the app then re-validates and applies nothing until the traveller confirms. The model gets trip data as labelled data with a "treat as data" rule (prompt injection), never private notes. The daily allowance lives in `users/{uid}/usage/{day}` and the rules let it only go up, so it can't be reset; credits are checked before and charged after the model answers (a provider outage costs nothing). Server code is in `api/`, tests in `src/server` (`ai.test.ts`, and `ai.emu.test.ts` against the emulators).
- The real model's behaviour (quality of replies, whether Gemini honours the function-calling format exactly) has only been tested against a stand-in provider until a key is added; check the first real replies and adjust `prompts.ts`/`tools.ts`.
- Provider resilience and speed (found with the real model): Gemini models are often briefly overloaded (503), so `post()` in `api/_lib/ai/gemini.ts` retries twice and then uses `AI_FALLBACK_MODEL` (default `gemini-3.5-flash-lite`) before any word reaches the traveller; other errors are not retried. Gemini 3 "thinks" before answering (seconds of delay), so requests send `reasoning_effort` (`AI_REASONING_CHAT` default `minimal`, `AI_REASONING_PLAN` default `low`; `off` omits it for providers that reject it). The 2.5 models are retired: an old `AI_MODEL` value shows up as `provider 404` in the chat error.
## M4 notes (push reminders with the app closed)
- Flow: the traveller allows notifications (the existing `PushPermissionCard`) → `notifications.push.register()` (`services/notifications/push.ts`, lazy through `lazy.ts`) gets an FCM token using the app's own service worker and stores it at `users/{uid}/devices/{id}` (`token`, `tz`, `platform`, `updatedAt`; rules fix that shape and let only the owner touch it). `NotificationEngine` re-registers on every load when permission is already granted (token changes, new account). Signing out / deleting the account first removes the record and the token (`stopPush` in `auth/firebase.ts`, best effort offline). If another account's record was left behind, `register()` mints a new token so the old record dies.
- Push exists only with `env.backend === 'firebase'` **and** `VITE_FIREBASE_VAPID_KEY` (the public Web Push key from Firebase → Cloud Messaging; config, not secret). Otherwise `noPush` is used and reminders stay in the app. While a device is registered the app no longer shows its own system notification (`deliver` in `notifications/mock.ts`), and the worker stays quiet when a window is visible: the in-app list is the same reminder.
- Worker: `public/push-sw.js` is pulled into the Workbox worker with `workbox.importScripts` (one worker per scope). Messages are data-only (`title`, `body`, `link`, `tag`); links must be same-origin paths (`safeLink`). It is plain script tested by evaluating it (`src/server/push.test.ts`). Needs `connect-src` for `fcmregistrations`, `firebaseinstallations`, `fcm` (in `security-headers.mjs`) and is excluded from the SPA rewrite and cached `no-cache` in `vercel.json`.
- Server: `api/push/sweep.ts` (`GET|POST`, `Authorization: Bearer $CRON_SECRET`) → `api/_lib/push/sweep.ts` `runSweep`: reads every device (collection group), each person's trips (`members.{uid}` IN roles), days/items/bookings of trips within 8 days of starting or running, runs `buildReminders` (`api/_lib/push/rules.ts`, a copy of the app's `rules.ts`; `src/server/push.test.ts` compares both every half hour around the seeded trips, so they cannot drift), skips types switched off in `users/{uid}.settings.notificationPrefs`, writes `users/{uid}/pushLog/{sha256(key)}` with create-if-absent **before** sending (so overlapping sweeps send once) and deletes it if Google was unreachable (retried next sweep), removes devices FCM reports `UNREGISTERED`. Reminders other than "next activity in 30 min" are held outside 08:00–21:00 in the device's timezone. `api/push/test.ts` sends a test to the caller's own devices (ID token, 1 a minute); the Settings "Send a test" button uses it. The weather alert is still app-only (needs a forecast fetch per trip).
- Credentials: `api/_lib/push/google.ts` signs a service-account JWT with Node crypto (no dependency) for Firestore + FCM. `FIREBASE_SERVICE_ACCOUNT` (the JSON from Firebase → Service accounts, or base64 of it) and `CRON_SECRET` are Vercel **Sensitive** variables, per scope. The service account bypasses the rules, so only `api/push/*` uses it. With `FIRESTORE_REST_URL` set (tests) the token is `owner`, which the emulator treats as admin; `FCM_SEND_URL` redirects sends.
- Scheduling: Vercel Hobby cron is once a day, so `vercel.json` has one daily run (`30 2 * * *`, 08:00 IST, Production only) for countdowns, and `.github/workflows/push-sweep.yml` calls the endpoint every 10 minutes for the 30-minute reminder (set variable `PUSH_SWEEP_URL` and secret `CRON_SECRET` in GitHub; scheduled workflows run from `main` only). Preview deployments are behind Vercel login, so on dev use the test button, or run `npm run dev` with the service account in `.env.development.local` and call `http://localhost:5173/api/push/sweep` with the bearer header.
- Known limits: a sweep scans all devices (fine at beta scale; shard or index by next-due time later); `pushLog` records are never pruned; destination names come from the id (`bali` → Bali) because the catalogue is not on the server; iPhone gets web push only from an installed app.
